# IA-06A — Conversation Core y consola interna

IA-06A agrega conversaciones multi-tenant de prueba fijadas a un Agent Version Draft o Testing. IA-06A soporta únicamente el canal `internal_test`; los canales externos no forman parte de esta fase. Una conversación puede estar `open`, `handoff_requested` o `closed`; handoff solicitado no implica asignación ni atención humana.

Cada turno persiste primero el mensaje de usuario cifrado y un assistant `pending`. Ambos quedan unidos a una identidad opaca del turno, generada exclusivamente en backend y almacenada como hash. La conversación conserva el hash del propietario vigente, el assistant asociado y los momentos de inicio, heartbeat y expiración. La transacción se libera antes de invocar el `ModelGateway`; no se mantiene ningún lock durante HTTP. Una segunda transacción bloquea y revalida conversación, placeholder, fencing token y Runtime Run antes de completar o fallar el turno. No existen retries automáticos. Los errores guardan sólo un código seguro.

`AI_CONVERSATION_TURN_LEASE_SECONDS` controla la vigencia máxima del propietario y `AI_CONVERSATION_TURN_FINALIZATION_MARGIN_SECONDS` reserva tiempo para persistir el resultado. El timeout HTTP efectivo del proveedor debe ser estrictamente menor que lease menos margen; una configuración insegura falla antes de persistir mensajes o hacer HTTP. Sin un heartbeat externo fiable, el modelo de liveness usa un timeout HTTP acotado y exige que tanto la expiración como el último heartbeat hayan vencido antes de recuperar. `created_at` nunca decide por sí solo el abandono.

La recuperación cerca el propietario anterior: marca su assistant `failed`, invalida el hash activo y termina sin invocar al proveedor. Un envío posterior reserva un token distinto. Cualquier callback tardío con el token antiguo se descarta y no puede completar mensajes, crear citas, cambiar handoff ni liberar un turno nuevo. Esto garantiza un único propietario lógico vigente y evita una segunda llamada mientras el propietario anterior sea válido; no promete entrega `exactly once` frente al proveedor cuando éste no ofrece idempotencia externa.

El Runtime Run registra el mismo hash del turno. Antes de asociarlo se carga con lock y se valida tenant, Agent, Agent Version, estado, propósito, modo de ejecución y token. La migración incremental añade claves compuestas que impiden físicamente asociar un mensaje a una conversación con otra identidad Agent/Version o a un Runtime Run con otra identidad de turno. Los registros existentes se rellenan sin descifrar contenido; un pending preexistente recibe una propiedad temporal recuperable.

La confirmación de Actions reutiliza exactamente el mismo ownership durable: conversación, assistant pending, Runtime Run y ActionRun comparten el hash, lease y deadline. Un Action en ejecución impide recovery normal. Si el deadline vence o el handler devuelve un resultado incierto, el turno se cerca, el ActionRun pasa a `reconciliation_required` y la conversación solicita revisión humana sin afirmar éxito o fallo ni volver a ejecutar el efecto.

El contexto multi-turn contiene como máximo seis mensajes `completed`, con tope configurable de 6,000 caracteres. Viaja como datos no confiables en `input.history`, separado de `instructions`; retrieval continúa usando principalmente el mensaje actual. No se persiste el prompt compilado.

El contenido usa el cast cifrado nativo de Laravel y sólo se lee mediante modelos tenant-scoped y servicios autorizados. Runtime Run mantiene observabilidad técnica, pero la consola no muestra proveedor, modelo, tokens, costos, IDs técnicos, prompts ni instrucciones. `AI_DATA_RETENTION_DAYS` documenta la ventana de retención (90 días por defecto); IA-06A no implementa purga automática.
